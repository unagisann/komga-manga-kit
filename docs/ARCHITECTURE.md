## 機能を追加する

新機能のBlueprintを作り、`Feature` を `built_in_features()` へ追加する。
機能ID、ラベル、画面のエンドポイント、アイコン、Blueprintの5点で登録する。
`base.html` が登録内容からナビゲーションを組み立てる。
テンプレートは `base.html` を継承し、共通部品は `components.html` を使う。
CSSは `tokens.css` の色・余白・書体・角丸を参照する。
整理の結果表示は `plan_results.html` と共通部品を使い、保存した全件結果から20件ずつ絞り込む。
静的資産のURLには内容のハッシュを付け、更新後のHTMLと以前のJavaScript/CSSの混在を防ぐ。

```python
from flask import Blueprint, render_template
from manga_kit.features import Feature

discovery = Blueprint("discovery", __name__)

@discovery.get("/discovery", endpoint="index")
def index():
    return render_template("discovery.html")

feature = Feature("discovery", "発見", "discovery.index", "search", discovery)
```

v0.2で機能が増えたら、`web.py` の各Blueprintを `features/` 配下へ分割できる。
登録側と共通UIへの変更は最小限にする。

## メタデータ取得元を追加する

主メニューと蔵書検索は共通ヘッダーに集約し、本文上のポータル・管理サブメニューは置かない。
`Feature.navigation` で同じBlueprint内の発見・新刊・アニメ・ランキングや完結移動・表紙修正を登録する。
`NavigationItem.related_endpoints` で詳細画面の選択表示を親の項目へ引き継ぐ。個別項目がない画面では `Feature.parent` の選択表示を使う。
ノーマライズ・補完・整理ルール・手動修正・処理履歴・設定・ロードマップは `/manage` の管理入口から開く。
`/` はポータルの入口をすぐ描画し、蔵書集計・各4作品の一覧と完結作品は `/api/portal/library` から後で読み込む。
この表示は既存の読み取りキャッシュを使い、ノーマライズの確認・実行や外部の補完を自動開始しない。
既存URLは維持し、旧作品編集URLも管理の配下として表示する。手動修正の一覧は `/manage/metadata`。

`MetadataProvider` の `id`・`label`・`inspect(path)` を実装する。
戻り値は `MetadataProposal(source, fields)`。取得元はファイルやKomgaへ書き込まない。
`create_app()` の取得元一覧へ登録すると、スキャン時に呼ばれる。
外部検索は `catalogs.py` の `id`・`label`・`configured()`・`search(query)` を持つ取得元で扱う。
`EnrichmentService` が選択した楽天Books・AniListを使い、デモではそれぞれ架空データへ切り替える。
検索結果は作品と情報源ごとに保持する。
別の取得元を追加する場合は、固有の候補IDと安全な情報源URL、検証した作品項目を返す。
スキャン中に蔵書全件について外部APIを呼ぶ設計にはしない。

優先順位: 作品フォルダの `series.json` → 書庫のComicInfo.xml → フォルダ/ファイル名。
`series.json` は独自形式とKomgaのMylar形式を読み取る。Mylar形式の状態は整理先を変えるため使わない。
複数巻で作品メタデータが異なる場合、作品名は最後に読み取った巻、それ以外は最初の非空値を使う。
巻数は各書庫の `Number` を優先する。後続の補完UIでは巻ごとの違いもレビューできるようにする。

## 整理・実行の分離

`plan_organization()` は共通モデルと設定から整理計画を返す純粋な処理。
実フォルダを指定した場合のみ、既存ファイルとシンボリックリンクによる整理先の逸脱を確認する。
大文字小文字・互換文字が異なる同一パスも衝突扱いにする。
読みが分からない作品は「その他」、巻数が分からない作品は「要確認」にする。

`OperationService` は明示的に有効にしたCLIだけから利用する。Web APIに実行エンドポイントはない。
`prepare` は全対象のSHA-256/XXH3-128・inode・デバイス・モード・更新日時、ローカル編集の版、Komgaの状態を保存する。
変更前情報は不変の `plan.json` と確認値へ、進捗は原子的に更新する `manifest.json` へ分ける。
更新前の記録はハードリンクで `manifest.previous.json` に保存し、ディレクトリを同期してから現行記録を置き換える。
現行記録が欠落・読み取り不能の場合は直前の版を使う。計画の確認値が一致しない場合は中止する。
実行直前と全件バックアップ後に再検証し、移動ごとに意図を記録する。
バックアップの内容・名前と親フォルダ、移動先の内容・名前と新しい階層を同期してから元パスを削除する。
POSIXのディレクトリ記述子を基準に操作し、シンボリックリンク・階層逸脱・異なるファイルシステムを拒否する。
同じライブラリの実行/復元は排他ロック、Webの編集保存は共有ロックを使う。

Komga連携は実機検証済みの1.29.0 / 1.29.1に限定し、現在のバイト列と解析済みハッシュの一致、一意性、作品全体の対応、ライブラリ設定を確認する。
移動後に明示的なAPIスキャンを要求し、内容一致による既読位置・読書日時・ロックした情報の引き継ぎを確認する。
書籍/作品IDの維持は前提にしない。復元直前に最新の既読状態を取得する。DBへ直接アクセスしない。
変換は `ConversionService` が元書庫を保持して別保存先へコピーする。同じ操作ID・確認値・排他ロックを使う。
ZIPは標準ライブラリ、RAR/7zはlibarchiveでブロック読み取りし、項目数・展開サイズ・名前・リンク・ComicInfoの参照を検証する。
書庫内の名前を実行データの展開先に使用せず、一時ディレクトリへ数字の名前で保持する。
全CBZを生成・CRC/SHA-256検証してから出力し、生成ファイルのinodeを公開前に記録する。停止後も自分の生成物だけを取り消せる。
復元・生成のコピー用一時ファイルは書き込み前にパス・デバイス・inodeを記録する。
再試行時は操作ID付きの名前・計画の親フォルダ・inodeを照合し、差し替えを拒否して一致する一時ファイルだけを削除する。
変換はKomga APIを使用しない。元書庫の置き換え、変換先への既読移行は未実装。
[整理実行ガイド](ORGANIZATION.md) と [CBZ生成ガイド](CONVERSION.md) に制約を記載する。

`KomgaMetadataService` は同じロック・計画/進捗の保存・確認値の検証を使うCLI専用の操作。
`prepare-metadata` でローカルの作品IDと項目を明示し（Komgaの作品はパス対応から特定）、作品名・並び順・出版社・あらすじ・ジャンル・タグを扱う。
`prepare-completion` は手動で完結にした作品のタグ・連載状態に限定し、`completion.py` の保持方針で変更後を作る。
どちらも同じ `komga_metadata` 操作を使い、完結情報の計画と結果には `mode: completion` を記録する。
ハッシュ・パスと書籍IDの一意な対応を確認し、値とロックの変更前/変更後を計画へ保持する。
Komga 1.29系の保存形式に合わせ、ジャンル・タグの変更後は小文字の集合へ正規化してレビューする。
既存の一覧は標準で追加方式、置き換え・ロック済み項目の変更はCLIの追加指定を必要とする。
ディスクへ実行意図を確定してから1回だけPATCHし、読み取りで結果を確認する。書籍・既読位置やスキャンAPIは変更しない。

`KomgaBatchService`（`komga_batch.py`）は複数作品の作品情報・完結情報・巻の著者を1計画にする。
書庫は内容を読まず、サイズ・inode・日時の属性と、Komgaのパス・巻構成・サイズ・解析済みハッシュ・IDで照合する。
Komgaのライブラリ単位の書籍・作品一覧を計画時と実行前後に1回ずつ取得し、作品ごとに送信予定を記録してからPATCHする。
復元は送信予定の作品を逆順に戻す。`KomgaReadingImportService`（`komga_import.py`）はKomgaの並び順から未設定の読みを
ローカル編集として取り込み、`StateStore.apply_operation_edits` で全作品を1トランザクションで保存・取り消しする。
通信結果不明・中断後の再実行は拒否し、選択項目が計画の反映前/反映後に一致する場合だけ明示的な復元を認める。
現行記録が欠落した場合の直前記録は復元にのみ使用し、変更前の記録だけが残った場合にも現在値と照合する。
ローカル編集と対象外のKomga項目は復元時に戻さない。
Komga側に条件付きPATCHがないため、最終確認後の他クライアントとの編集競合は防げない。
対象作品の同時編集・自動取り込みを止める前提とし、詳細は [Komga反映ガイド](KOMGA_METADATA.md) に記載する。

`KomgaAuthorsService` は作品照合・保存・ロックの基盤を共用し、独立した `komga_authors` 操作で巻の著者を扱う。
`authors.py` の候補生成はローカルの確認用で、反映には名前・役割を明示指定する。
全対象の変更前後・ロック・巻IDを保存し、各PATCH前に送信意図を同期して、送信直前・直後にも全対象を検証する。
1計画50巻まで。既存一覧の順番・役割を保持し、復元は逆順で計画前/後との一致を確認する。
通信結果不明からの再送と、未送信巻への第三者の編集の巻き戻しを拒否する。
詳細は [著者反映ガイド](AUTHORS.md)、保存先の復旧と計画の同一性は [運用ガイド](OPERATIONS.md) に記載する。

## 編集・ジョブ・操作履歴

スキャン結果は30秒のメモリキャッシュを使い、編集はそのコピーへ適用する。
通常の期限切れ・起動後の読み取りでは、組み込み取得元の書庫メタデータをSQLiteの `archive_metadata_cache` から再利用する。
相対パス・取得元/解析形式の版・デバイス/inode・サイズ・mtime/ctimeの一致を必要とし、変更された書庫だけ開き直す。
フォルダとsidecarは再確認し、新規/削除・ローカル編集を反映する。独自の取得元・エラー・読み取り中に変わった書庫は再利用しない。
`refresh=True` の指定だけなら表示用キャッシュを使わず、書庫を読み直す。CLIの実行前検査や保存前の確認は従来の読み取りを維持する。
読み取り専用の整理プレビューだけは `refresh=True, reuse_metadata=True` を使い、現在のファイル一覧・属性・sidecarを確認しつつ未変更の書庫を再利用する。
配置計算と衝突確認は全冊に行ってからジョブへ保存し、検索・状態別表示・20件ずつのページ送りでは保存済み結果を使う。
通常の蔵書整理GETはスキャンや配置計算を行わず、現在の設定と同じルールの直近結果、または結果URLで指定された記録を表示する。
Webは期限切れ後のファイル確認も共有ワーカーへ任せ、直前の結果を直ちに返す。重複した確認はキューへ積まず、失敗時も30秒以内に再試行しない。
明示的な再スキャン中も通常の閲覧は直前のスナップショットを使う。初回の結果がない場合は読み取り完了を待つ。
キャッシュはライブラリごとの名前空間に保存する。DBスキーマの版は3のまま、再生成可能なテーブルだけを追加した。
取得元の解析仕様を変える場合は `scan_cache.CACHE_VERSION` を更新し、旧結果を再利用しない。
蔵書一覧とメタデータ一覧は60作品ずつ表示し、検索・状態・五十音を保ってページを移動する。
変更した項目だけを保存するため、未編集の項目はComicInfo.xmlやseries.jsonの更新を引き続き反映する。
編集と操作履歴は同じSQLiteトランザクションで保存する。作品ごとの版で同時編集を検出する。
保存直前には再スキャンし、差分確認時の書庫情報の指紋と比較する。

ジョブは一つのアプリプロセス内で逐次実行し、処理待ちは最大20件。
Webからはスキャン・整理プレビューと、明示的に有効化したノーマライズ・復元を実行できる。CLIの整理実行・復元も同じ履歴へ記録する。
`normalization.py` は書庫の属性・作品情報・ルールを保存し、追加・変更分の書庫検証と命名計画を一つにまとめる。
Web実行は既存の操作ロック・バックアップ・復元を共用し、内容を変えるCBZをすべて検証してから原本を置き換える。
生成物の照合情報を公開前に保存し、原本削除直後の停止からも元書庫を復元できる。
Komga 1.29.1では `managed_rebuild.py` が、既存のハッシュ復元を使う移動と、同じパスでの再生成を別の操作記録へ分ける。復元も元のバイト列を戻して検証してから逆移動する。
対象数の進捗、結果、開始・終了・失敗を保存する。
POSIX環境では再起動時に停止したプロセスのジョブを「中断」にする。Linuxではプロセス開始情報でPIDの再利用も検出する。
Windowsでのネイティブ実行では中断の自動判定は行わない。Dockerでの実行はLinuxの判定を使う。
停止したジョブは自動再開しない。利用者が再実行する。多ホストで共有するジョブキュー・定期実行は未導入。

DBは `data.root` に置き、デモ/実ライブラリとライブラリのルートで名前空間を分ける。
スキーマ2は移動/復元ごとの編集移設結果も保存する。編集移設と操作履歴は同じトランザクションで確定し、
JSON記録更新の前に停止しても、DBの結果から復元できる。旧スキーマ1の編集・ジョブは保持する。
各SQLite接続で `synchronous=FULL` を指定し、WALのコミットを同期する。
同期エラーは処理を中止する。[保存と中断からの復元](DURABILITY.md) に保存順序と検証の限界を記載する。
APIやCLIはAPIキー・任意の認証トークンを状態DBへ保存しない。
スキーマ3は編集行に補完元の `provenance` を追加する。情報源・候補ID・URL・取得日時・採用/調整項目を保持する。
補完元の変更は編集の版も進めるため、作成済みの整理計画と同時編集の確認に含まれる。
整理・復元では補完元も同じトランザクションで移設し、手動編集で値が変わった項目は補完元の採用一覧から外す。
対応付けの解除は保存済みの作品項目を保持し、編集の全解除は補完元も解除する。
検索キャッシュは別テーブルで1時間・ライブラリごと100件まで保持し、期限切れは起動・検索時に削除する。
候補の採用時もライブラリ・作品・取得元・期限を再検証し、ブラウザが指定した情報源URLは受け付けない。
楽天は1.1秒、AniListは2.1秒の検索間隔と429の待機期限を情報源ごとにDBでプロセス間共有する。自動再試行は行わない。
AniListは公開GraphQLへ固定クエリと変数を送り、漫画だけを検索する。総件数・最終ページは使わず `hasNextPage` で送る。
ネタバレ指定・判定不明のタグはキャッシュへ保存する前に除外する。情報源URLは検証した数値IDから生成する。
ジャンル・タグは共通モデルの文字列配列で保持し、各100個・各100文字に制限して重複を取り除く。
ComicInfoのGenre/Tags、series.json、手動編集・外部補完を同じ項目へ適用する。

補完APIの `provider` は `rakuten_books`（省略時）か `anilist` を指定する。デモの情報源は内部で置き換える。
作品情報APIの `provenances` は、この2つのキーで情報源ごとの対応付けを返す。
従来の `provenance` は楽天Books側の単一の対応付けとして維持する。
状態DBのJSONは従来の単一リンクと複数リンクのマップを読める。楽天側のみの保存は旧形式を維持し、
既存の整理操作の編集スナップショットを自動変換しない。SQLiteのスキーマは3のまま。
新規の補完リンクは `identity`（候補の作品名/別名・商品名・出版社・レーベル・巻・版・読者層の根拠）と
`match`（保存時の一致/要確認理由）も保持する。既存リンクには追加を強制しない。
検索結果の `match` はキャッシュへ固定せず、現在の編集と確認済み別名から再計算する。採用確認・保存時も再照合する。
検索キャッシュの仕様番号は3。以前の検索は再利用・採用せず、保存済み編集や整理操作のスナップショットは変更しない。
追加・変更・解除は選択した情報源だけに適用し、手動編集は変更項目の出典を外す。編集の全解除はすべての対応付けを外す。
自動補完の候補は `enrichment` ジョブの `rows` に根拠・差分・元の編集と書庫の指紋を保存する。
保存時は1回の現在スキャンと全対象の編集・検索期限を検証し、`operation_edits` の `enrichment` 方向へ一括確定を記録する。
既存の整理との編集ロックを共有し、1件の衝突でも全件を保存しない。同じ結果の再送は記録から二重適用を防ぐ。
CLIのファイル変更やKomgaの書き込みをWebへ公開しない。DBスキーマは3のまま。
既定のGunicornは1ワーカー。複数プロセス・複数ホストを使う分散実行は今後の対象とする。

ジョブ受付例:

```json
{"kind": "preview", "layout": {"completed": "{author}/{series}"}}
```

編集の差分確認例:

```json
{"fields": {"reading": "アメアガリノキッサシツ"}}
```

保存時は同じ入力に、差分確認の応答の `revision` と `base_fingerprint` を付ける。
編集解除は `{"reset": true}` の差分確認後、同じ版と指紋を付けて保存する。

## 既存Tools相当の機能

`inventory.py` がローカル作品とKomgaのIDをまとめ、`feeds.py`・`new_volumes.py`・`reading.py` が明示更新した結果を `tool_cache` へ保存する。
`tools_web.py` はポータル、`tools_admin.py` は管理機能。共通テンプレートと機能登録を使う。
`preferences.py` は非秘密の設定を検証して共有し、`credentials.py` は環境変数優先・専用ファイルで認証情報を扱う。
`smart_shelves.py` はアプリが作成したIDだけを確認付きで同期・復元する。
`page_editor.py` はページ対応表と既存のバックアップ・復元処理を使い、`ai_assist.py` は提案・入力指紋・保存前の編集を保持する。
`automation.py` はアプリ内の日次実行・取り込み後処理・段階別の再開を担当し、外部の既存タイマーを操作しない。
