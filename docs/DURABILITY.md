# 保存と中断からの復元

0.1.0.dev4では、整理・復元・CBZ生成の内容とファイル名がディスクに確定する順序を補強した。
POSIXの `fsync` を使用し、同期の失敗は処理を中止する。ファイルの同期だけでは親ディレクトリの名前は
確定しないため、両方を同期する。[Linuxのfsync仕様](https://man7.org/linux/man-pages/man2/fsync.2.html)

## 移動の保存順序

1. 全対象のバックアップをコピーし、SHA-256を確認する。
2. バックアップの内容、保存先ディレクトリ、新しい操作用の親フォルダを同期する。
3. 操作記録へ次の移動の意図を保存し、記録の内容・名前を同期する。
4. 新しい移動先フォルダとその親を同期し、元ファイルのハードリンクを移動先へ作成する。
5. 元と先を検証し、移動先のファイル内容と親ディレクトリを同期する。
6. 元の名前を削除し、元の親ディレクトリを同期する。
7. 完了した移動を操作記録へ保存する。

移動先の同期に失敗した場合は元の名前を削除しない。元の名前を削除した後で同期に失敗した場合も、
確定した移動先を保持する。復元で逆方向へ移動する場合も同じ順序を使用する。
同期回数が増えるため、以前より処理に時間がかかる場合がある。

## 操作記録と編集の保存

確認済みの不変の計画は `plan.json`、進捗と復元したinodeは `manifest.json` に保存する。
現行記録を更新する前に、直前の記録を `manifest.previous.json` として確定する。
新しい記録は一時ファイルへ書いて同期し、現行記録と原子的に置き換えて操作フォルダを同期する。

現行記録が欠落している・JSONとして読めない場合は直前の記録を使用する。
確認値の不一致や計画・両方の記録の破損を無視して実行する機能はない。
0.1.0.dev2/dev3の記録も読み取れるが、以前の実行に直前の記録や一時ファイルの記録は追加されない。

SQLiteはWALを使用し、各接続で `synchronous=FULL` を明示する。
編集の移設と履歴は同じトランザクションで確定し、JSON記録の更新前に停止した場合はDBの結果も参照して復元する。
WALでのFULL同期はコミットごとにWALを同期する。[SQLiteの同期設定](https://www.sqlite.org/pragma.html#pragma_synchronous)

## 停止後の復元

アプリは中断した実行を自動再開しない。CLIの `operation` で状況を確認し、同じ設定・操作ID・確認値で
`restore` を実行する。整理は元の名前へ戻し、CBZ生成は変更されていない自分の生成物を取り消す。
コマンドは [整理実行ガイド](ORGANIZATION.md) と [CBZ生成ガイド](CONVERSION.md) を参照する。

バックアップからの復元・CBZの配置は、一時ファイルへコピーして内容を同期した後、正式な名前へ公開する。
コピー前に `.manga-kit-restore-<操作ID>-<ランダム値>` のパス・デバイス・inodeを記録する。
再試行時は計画の親フォルダ・操作ID付きの名前・inodeが一致するものだけを削除し、必要ならコピーし直す。
別のファイルに差し替えられている場合は削除せず中止する。

一時ファイル作成から記録保存までの間で停止した場合や、以前の版で作られた一時ファイルは記録がない。
それらと実行データ内の一時作業フォルダは自動削除しない。操作が終了した後に個別に確認する。
操作フォルダ・バックアップ・状態DBは復元が不要と判断するまで保持する。

## 検証した範囲

Linux上で同期エラーを注入し、未同期の名前が失われるモデルで、元の削除前に移動先の内容・名前・階層が
確定していることを確認する。別プロセスへ `SIGKILL` を送り、ハードリンク直後、元の名前の削除直後、
復元・CBZコピーの途中と公開直後、編集DB確定直後から復元・取り消しを検証する。
実行時の詳細な結果は [検証記録](VALIDATION.md) を参照する。

実際のPiの電源遮断や媒体故障は検証していない。プロセスの強制終了は、OS・デバイスのキャッシュを
失う物理的な電源断と同じ条件ではない。保存の保証はファイルシステム・OS・ストレージが同期要求を正しく
処理することを前提とし、電源断時の媒体故障や同期要求を無視する機器をこの実装だけで防ぐことはできない。
ネットワークファイルシステムでの耐久性は未検証。別媒体のバックアップやUPSを置き換える機能ではない。
