# 書誌検索と作品情報の補完

0.1.0.dev5は、楽天Booksで代表巻の書誌情報を探し、作品名・読み・著者・出版社を項目ごとに補完する。
採用する情報は利用者が選び、このツールの状態DBへ保存する。蔵書検索・五十音分類・整理計画に反映する。

## デモで試す

既定の `app.demo: true` では認証情報なしで架空の書誌データを検索できる。
「メタデータ」→「月を待つ駅」→「候補を探す・対応付けを確認」→「候補を検索」と進む。
候補を選ぶと、未設定の読みと著者にチェックが入る。採用内容を確認して保存すると、五十音の「た」行へ分類される。
デモでは楽天への通信は行わず、実在する作品のデータを同梱しない。

## 楽天Booksを設定する

[楽天ウェブサービス](https://webservice.rakuten.co.jp/guide)で自分のアプリを登録し、アプリIDとアクセスキーを取得する。
アプリ種別・利用目的・許可するサイト・APIアクセス設定は自分の利用環境に合わせる。

```yaml
app:
  demo: false
library:
  root: /path/to/your/manga
rakuten:
  enabled: true
  application_id_env: RAKUTEN_APPLICATION_ID
  access_key_env: RAKUTEN_ACCESS_KEY
  origin: ""
  timeout_seconds: 10
```

シェルの環境変数 `RAKUTEN_APPLICATION_ID` と `RAKUTEN_ACCESS_KEY` に値を設定して起動する。
ComposeではGit対象外の `.env` に設定する。キーを入力するWeb画面はなく、YAMLへキーの値を保存しない。
設定変更後はアプリを再起動する。設定画面で認証情報の登録状況を確認できる。

登録済みの自分のサイトのオリジンを送る場合は、`rakuten.origin: https://manga.example.com` のように指定する。
指定値をOriginとRefererヘッダーへ設定する。認証情報・クエリ付きURLや任意のAPI接続先は受け付けない。
実APIの認証接続は未検証。403等の場合はキーに加え、楽天側のアプリのアクセス設定も確認する。

## 検索・確認・保存

1. メタデータの作品詳細から「候補を探す・対応付けを確認」を開く。
2. 作品名・著者、または13桁のISBNを入力して検索する。ISBNを入力した場合は作品名・著者より優先する。
3. 巻数・新装版・著者を見て代表巻を選ぶ。検索順位による自動対応付けは行わない。
4. 必要な項目にチェックを入れる。未設定の項目だけが最初から選択される。
5. 巻数を含む作品名・読みなどは作品単位に修正し、「採用内容を確認」で差分を見る。
6. 「対応付けと選んだ情報を保存」で確定する。すべて未選択なら対応付けのみ保存できる。

楽天Booksの書誌タイトルをそのまま候補にする。巻数の自動除去、レーベル名からの作品名推定、連載完結の推定は行わない。
あらすじ・画像・価格・在庫は取得しない。書庫のComicInfo.xmlやseries.json、Komgaへの反映は今後の段階で追加する。
検索時は入力した作品名・著者・ISBNとページ条件を楽天へ送信する。蔵書のパスや書庫の内容は送信しない。

## 対応付けと情報源

保存した作品には情報源・候補ID（楽天ではISBN）・情報源URL・取得日時を記録する。
採用項目と、候補から利用者が修正した項目も保持する。作品情報の画面と操作履歴で確認できる。

誤った巻・別作品を選んだ場合は、再検索して別の候補へ対応付けるか「対応付けを解除」を使う。
解除だけでは既に採用した作品情報は戻らない。必要な項目を手動編集するか、作品情報画面の
「読み取った情報に戻す」で手動編集と補完をまとめて解除する。
別候補へ変更する際、今回選ばなかった項目の値は保持する。以前の候補の項目別の出典は引き継がない。

手動編集で値を変えた項目は、補完元の採用項目一覧から外す。整理・復元時には対応付けも作品と一緒に引き継ぐ。
書庫・編集が差分確認後に変わった場合や、整理・復元中の保存は中止し、再確認を求める。

## 検索の保存期間と通信制限

- 検索結果は1時間、ライブラリごとに最大100回分を `data.root/state.sqlite3` に保持する。
- 同じ作品・同じ検索条件の結果は再利用する。取得日時は画面に表示し、期限切れの候補は採用できない。
- 期限切れは起動・検索時、上限を超えた古い結果は検索時に削除する。アプリ停止中には削除処理は動かない。
- 同じ実行データを使うプロセス間で、検索間隔を最低1.1秒空ける。
- 429は待機期限を記録する。Retry-Afterが秒数の場合は最大1時間まで採用し、その他は60秒待つ。
- タイムアウト・制限・障害時の自動再試行は行わない。利用者が必要に応じて再検索する。

保存した編集と対応付けは検索キャッシュと分けて保持する。APIキーと生の応答全体はDBへ保存しない。
検索キャッシュを含む実行データは私用データとして扱い、リポジトリへ追加しない。

## APIと検証範囲

[楽天Books書籍検索API](https://webservice.rakuten.co.jp/documentation/books-book-search)の
`https://openapi.rakuten.co.jp/services/api/BooksBook/Search/20170404` を使用する。
アプリIDはクエリ、アクセスキーはヘッダーへ渡す。コミックに絞り、1ページ10件、最大100ページ。
リダイレクトを追わず、応答サイズ・型・文字数・情報源URLを検証する。

楽天検索を有効にした実ライブラリの画面では、[公式のクレジット表示](https://webservice.rakuten.co.jp/guide/credit)を掲載する。
利用時のデータの取り扱いは、[楽天のキャッシュ・更新に関する案内](https://webservice.faq.rakuten.net/hc/ja/articles/900001974343)も確認する。

公式仕様に基づく模擬応答、架空データのブラウザ操作、保存・解除・移動・復元を検証する。
実APIのアプリ登録・認証接続・実際の検索応答は未検証。AniList等の追加取得元とKomgaへの書き込みは未実装。
具体的な結果は [検証記録](VALIDATION.md) を参照。
