# 書誌検索と作品情報の補完

現行の開発版は、楽天Booksの書誌情報・AniListのタグ・ジャンルの補完と、選んだ作品項目のKomgaへの反映を提供する。
楽天Booksでは代表巻の作品名・読み・著者・出版社、AniListでは作品単位の分類を選ぶ。
採用する情報は利用者が選び、このツールの状態DBへ保存する。蔵書検索・五十音分類・整理計画に反映する。

## デモで試す

既定の `app.demo: true` では認証情報なしで架空の書誌データを検索できる。
上部の「自動補完」で「月を待つ駅」を選び、「選んだ作品の候補を自動取得」と進む。
補完する読み・著者などを確認して「不足情報をまとめて保存」を押すと、五十音の「た」行へ分類される。
デモでは楽天への通信は行わず、実在する作品のデータを同梱しない。
「補完する情報」で「ジャンル・タグ（AniList）」を選んでも同じ流れを試せる。こちらも架空データを使い、通信しない。

## 普段の使い方と管理

主メニューは「ホーム」「蔵書」「自動補完」「管理」。通常は「自動補完」から不足情報を補う。
「管理」に蔵書整理・作品情報の手動修正・処理履歴・設定・ロードマップをまとめた。
手動修正は、取得できない項目や誤った情報を修正するために使う。既存の操作URLと保存済み編集・履歴は保持する。

1. 「自動補完」で書誌情報（楽天Books）かジャンル・タグ（AniList）を選ぶ。不足項目を作品ごとに表示する。
2. 対象を選び「候補を自動取得」を押す。1回60作品まで、利用者が選んだ作品名だけを送信する。
3. 作品名/確認済み別名・著者・出版社・版を照合し、「補完候補」「個別確認」「取得できない」「取得失敗」に分ける。
4. 補完候補の内容を確認し、空欄だけをまとめて保存する。既存の値を上書きしない。候補取得だけでは作品情報を変えない。
5. 個別確認が必要な作品は候補を選び直す。取得できない項目は「管理で手動修正」へ進む。

書誌候補は、完全一致する作品名に加え著者・出版社・保存済み対応付けの根拠がある場合に絞る。
同名別著者・出版社や版の矛盾、短い作品名、検索結果に未表示候補が残る場合は個別確認にする。
同じ版の複数巻は第1巻を一意に選べる場合だけ候補にする。第2巻以降や、複数巻の作品で巻数不明の候補からあらすじを補わない。
AniListは著者・出版社を返さないため、全結果が1件で作品名/確認済み別名が完全一致する場合だけ確認用の補完候補にする。
候補の自動選択は同一作品の保証ではなく、保存前に内容を確認する。

取得の進捗と結果は処理履歴に残り、画面を離れても取得を続ける。再起動後も完了済みの結果を確認できる。
取得中にサーバーが停止した処理は中断として扱い、自動再開しない。
通信間隔を守って順番に取得し、429等の待機指示では残りの検索を中止する。自動再試行はしない。
保存前に現在の書庫・編集・検索期限を再確認し、1作品でも変更・期限切れがあれば全件の保存を中止する。
確認済みの一括保存はDBでまとめて確定し、同じ結果を再送しても二重適用しない。
Komgaへの反映と書庫の移動・復元は、従来どおり確認付きCLIで別途実行する。

## AniListを設定する

```yaml
app:
  demo: false
anilist:
  enabled: true
  timeout_seconds: 10
```

設定変更後はアプリを再起動する。公開の漫画情報だけを取得するため、APIキー・ログインは不要。
自動補完の「補完する情報」で「ジャンル・タグ（AniList）」を選ぶ。個別確認画面では作品名で検索できる。
候補の日本語名・別表記・初出年・国と、情報源の作品ページを見て、同名の別作品でないことを確認する。
漫画・読切（MANGA / ONE_SHOT）に絞り、作品名を検索変数として送る。著者・ISBN検索、確認なしの対応付けは行わない。

ジャンル・タグをそれぞれ選択し、1行に1項目で修正して差分を確認する。
**採用する一覧は現在の一覧を置き換える。** 残したい項目も入力する。未選択の項目は変更しない。
空欄を採用すれば一覧を空にできる。各100個以内・各100文字まで。前後の空白と大文字小文字だけが違う重複を除く。
AniListのジャンル・タグは閉じた語彙なので、同梱の確認済み対訳表で日本語にする（AIによる都度の翻訳はしない）。
Komgaはジャンル・タグを小文字で保存するため、英字だけの訳語は使わない。対訳表にない新しい語は取得元の表記のまま提示する。
読者層のタグ（少年・青年・少女・レディース・児童）はKomgaの読者層表示に合わせてジャンルに含める。
成人向けのタグ・Sexual Content分類・Hentaiジャンル、関連度（rank）60未満のタグ、ネタバレ指定・判定不明のタグは候補・キャッシュから除外する。
関連度60の基準は既存KomgaToolの実測による。候補のタグは取得順で最大100個を提示する。
作品情報画面から手動でも編集でき、蔵書の検索語にも使える。

接続先は `https://graphql.anilist.co` に固定する。入力した作品名とページ条件だけを送り、
ライブラリの保存先・書庫・Komgaの情報・読書情報は送信しない。起動・スキャン・画面表示では検索しない。
表紙・本文・あらすじ・ユーザー情報は要求しない。情報源のURLは作品IDから生成する。
総件数と最終ページの精度に関する[公式のページング案内](https://docs.anilist.co/guide/graphql/pagination)に従い、次ページの有無だけでページを送る。
個別検索は1ページ10件・最大100ページ。自動補完は選んだ60作品までの先頭ページを順番に検索する。
選択していない全蔵書の収集や定期収集は行わない。
利用にあたっては [AniListの利用条件](https://docs.anilist.co/guide/terms-of-use) を確認する。

## 楽天Booksを設定する

[楽天ウェブサービス](https://webservice.rakuten.co.jp/guide)で自分のアプリを登録し、アプリIDとアクセスキーを取得する。
アプリ種別・利用目的・許可するサイト・APIアクセス設定は自分の利用環境に合わせる。

```yaml
app:
  demo: false
library:
  root: /path/to/your/manga
rakuten:
  enabled: true
  application_id_env: RAKUTEN_APPLICATION_ID
  access_key_env: RAKUTEN_ACCESS_KEY
  origin: ""
  timeout_seconds: 10
```

シェルの環境変数 `RAKUTEN_APPLICATION_ID` と `RAKUTEN_ACCESS_KEY` に値を設定して起動する。
ComposeではGit対象外の `.env` に設定する。キーを入力するWeb画面はなく、YAMLへキーの値を保存しない。
設定変更後はアプリを再起動する。設定画面で認証情報の登録状況を確認できる。

登録済みの自分のサイトのオリジンを送る場合は、`rakuten.origin: https://manga.example.com` のように指定する。
指定値をOriginとRefererヘッダーへ設定する。認証情報・クエリ付きURLや任意のAPI接続先は受け付けない。
実APIの認証接続は未検証。403等の場合はキーに加え、楽天側のアプリのアクセス設定も確認する。

## 検索・確認・保存

1. 自動補完の結果から「候補を個別に確認」、または管理の手動修正から「候補を探す・対応付けを確認」を開く。
2. 作品名・著者、または13桁のISBNを入力して検索する。ISBNを入力した場合は作品名・著者より優先する。
3. 巻数・新装版・著者・発売日を見て代表巻を選ぶ。あらすじを使う場合は第1巻を選ぶ。検索順位による自動対応付けは行わない。
4. 照合理由と要確認の理由を読み、必要な項目にチェックを入れる。要確認の候補はすべて未選択で始まる。それ以外は未設定の項目だけが最初から選択される。
5. 必要なら作品単位に修正し、「採用内容を確認」で差分を見る。
6. 「対応付けと選んだ情報を保存」で確定する。すべて未選択なら対応付けのみ保存できる。

検索は楽天Booksのジャンル「漫画（コミック）」（001001）に限定する。判型のコミック指定と違い、漫画文庫も含む。
作品名・読みは、商品名の末尾にある空白・括弧・「第」で区切られた巻数とレーベル注記を除いて候補にする。
レーベルらしい括弧は巻数の直後にある場合だけ除き、「特装版」等の明確な版表記も除く。
「作品（続編）」等の副題や、判別できない括弧は作品名・読みに保持する。
「ゴルゴ13」のように作品名へ直接続く数字は残す。候補カードには元の商品名・巻数・発売日を表示する。
あらすじは商品説明から販促・版の案内の行（累計部数、特典、電子限定、※の注記など）を除き、400文字以内にした候補を出す。
販促しか残らない説明はあらすじの候補にしない。巻が進んだ回の惹句を避けるため、第1巻を代表巻に選ぶ。
読者層は楽天のジャンル（少年・少女・青年・レディース）、またはレーベルの明示的な読者層表記から一意に決まる場合だけジャンルの候補にする。
レーベルは `seriesName` を出版社と分けて表示する。「少年コミックス」「少女漫画」等、読者層の語にコミック/漫画/まんが/マンガが続く場合だけ判定する。
「架空コミックス」や「少年の冒険コミックス」からは推定しない。複数の読者層が現れる場合と、ジャンルとレーベルが矛盾する場合は提案しない。
レーベル名から出版社・作品名を推定せず、連載完結の推定も行わない。画像・価格・在庫は取得しない。
書庫のComicInfo.xmlやseries.jsonは変更しない。楽天Kobo（電子書籍）での補完は後続版の対象。
保存済みの作品情報は、別途CLIで項目を選び、確認値を指定してKomgaへ反映できる。
検索時は入力した作品名・著者・ISBNとページ条件を楽天へ送信する。蔵書のパスや書庫の内容は送信しない。

## 候補の照合理由・別名・版違い

候補カード・採用項目・保存前の差分画面で、作品名/別名・著者一覧・出版社の一致と要確認の理由を表示する。
全半角・かな・空白・英字の大文字小文字を正規化した完全一致だけを照合に使い、部分一致では確定しない。
短い作品名、比較できる著者がない場合、著者一覧や出版社が異なる場合は要確認にする。
同じページ内で同名・別著者/出版社/レーベル/版の候補が複数ある場合も、利用者が代表巻を選ぶ。
一致は同一作品の保証ではない。副題や関連本を含め、情報源の作品ページを確認する。

通常版・文庫版・新装版・愛蔵版・完全版・特装版・限定版・カラー版・合本版の明示的な表記を表示する。
文庫は楽天の判型または末尾が「文庫」のレーベルからも判定する。表記がない商品を通常版と断定しない。
ローカルの作品名/作品フォルダと候補の版表記が異なる場合や、片方にしかない場合は要確認にする。
照合時だけ末尾の明確な版注記を除いて比較する。保存する候補の作品名・不明な副題を無条件に変えない。

候補を確認して対応付けると、作品名と別表記（AniListの日本語/ローマ字/英語名）も情報源に保持する。
次の検索では「確認済みの別名」ボタンで検索語を選べ、照合にも使う。ボタンだけでは通信せず、「候補を検索」で送信する。
検索語を入力しただけでは確認済みの別名にならない。対応付けを解除・変更するとその情報源の旧別名も外れる。
既存の対応付けに別名を追加するには再検索して確認・保存する。未選択の項目や保存済みの読みは変更しない。
今回の対象は楽天Books・AniList。openBD・Wikidata等の新しい連携は追加していない。

## 対応付けと情報源

保存した作品には情報源・候補ID（楽天ではISBN）・情報源URL・取得日時を記録する。
採用項目と、候補から利用者が修正した項目も保持する。作品情報の画面と操作履歴で確認できる。
新しく対応付けた候補は元の商品名・著者・出版社・レーベル・巻・版・読者層の根拠と、保存時の照合理由も保持する。
検索キャッシュを再利用するときと採用内容の確認時は、現在の作品情報と照合し直す。

誤った巻・別作品を選んだ場合は、再検索して別の候補へ対応付けるか「対応付けを解除」を使う。
解除だけでは既に採用した作品情報は戻らない。必要な項目を手動編集するか、作品情報画面の
「読み取った情報に戻す」で手動編集と補完をまとめて解除する。
別候補へ変更する際、今回選ばなかった項目の値は保持する。以前の候補の項目別の出典は引き継がない。

手動編集で値を変えた項目は、補完元の採用項目一覧から外す。整理・復元時には対応付けも作品と一緒に引き継ぐ。
書庫・編集が差分確認後に変わった場合や、整理・復元中の保存は中止し、再確認を求める。
楽天BooksとAniListの対応付けは同時に保持する。補完・対応変更・解除は、画面で選んだ情報源だけに適用する。
「読み取った情報に戻す」は両方の対応付けと手動編集をまとめて解除する。
Komgaへ反映した情報はローカルの対応解除や編集解除だけでは戻らない。反映時の操作IDから復元する。
作品名・読み・出版社・あらすじ・ジャンル・タグの反映と、変更前の値・ロックの復元は [Komga反映ガイド](KOMGA_METADATA.md) を参照。
著者などの巻単位の書き込みは対象外。

## 検索の保存期間と通信制限

- 検索結果は1時間、ライブラリごとに最大100回分を `data.root/state.sqlite3` に保持する。
- 補正仕様の変更前に作った検索結果は再利用・採用せず、再検索を求める。保存済みの編集・情報源・操作履歴は保持する。
- 同じ作品・同じ情報源・同じ検索条件の結果は再利用する。取得日時は画面に表示し、期限切れの候補は採用できない。
- 期限切れは起動・検索時、上限を超えた古い結果は検索時に削除する。アプリ停止中には削除処理は動かない。
- 同じ実行データを使うプロセス間で、楽天は最低1.1秒、AniListは最低2.1秒の検索間隔を情報源ごとに共有する。
- 429は待機期限を記録する。Retry-Afterが秒数の場合は最大1時間まで採用し、その他は60秒待つ。
- AniListが成功応答で残り回数0を返した場合も60秒待つ。[公式の制限案内](https://docs.anilist.co/guide/rate-limiting)を参照。
- タイムアウト・制限・障害時の自動再試行は行わない。利用者が必要に応じて再検索する。

保存した編集と対応付けは検索キャッシュと分けて保持する。APIキーと生の応答全体はDBへ保存しない。
検索キャッシュを含む実行データは私用データとして扱い、リポジトリへ追加しない。

## APIと検証範囲

[楽天Books書籍検索API](https://webservice.rakuten.co.jp/documentation/books-book-search)の
`https://openapi.rakuten.co.jp/services/api/BooksBook/Search/20170404` を使用する。
アプリIDはクエリ、アクセスキーはヘッダーへ渡す。ジャンル「漫画（コミック）」に絞り、1ページ10件、最大100ページ。
取得する項目は書名・読み・著者・出版社・レーベル（seriesName）・判型（size）・ISBN・商品URL・商品説明・発売日・ジャンルID。
リダイレクトを追わず、応答サイズ・型・文字数・情報源URLを検証する。

楽天検索を有効にした実ライブラリの画面では、[公式のクレジット表示](https://webservice.rakuten.co.jp/guide/credit)を掲載する。
利用時のデータの取り扱いは、[楽天のキャッシュ・更新に関する案内](https://webservice.faq.rakuten.net/hc/ja/articles/900001974343)も確認する。

公式仕様に基づく模擬応答、架空データのブラウザ操作、保存・解除・移動・復元を検証する。
楽天の実APIのアプリ登録・認証接続・実際の検索応答は未検証。
AniListは2026-10-14に架空の検索語で公開APIへ接続し、0件の正常応答を確認した。
実在作品の候補照合・実運用の利用制限は未検証。Komgaの作品情報の書き込み・復元は隔離した1.29.0で検証した。
具体的な結果は [検証記録](VALIDATION.md) を参照。
